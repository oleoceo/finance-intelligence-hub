## Implementation Sequence

1. **Add Kysely dependency** to `packages/database/package.json`:
   - `kysely` (provides query builder, PostgresDialect, and Migrator API)
   - Do NOT install a separate `kysely-migrator` package — ADR-001 selected Kysely's own Migrator
   - `pg` is already owned by `packages/database/package.json` as runtime dependency

2. **Create migration directory structure** under `packages/database/`:
   ```
   packages/database/migrations/
   ├── 001_technical_validation.ts
   └── README.md (migration conventions, TypeScript build considerations)
   ```
   Choose a layout that works with TypeScript build/local/CI execution. Do not create competing migration directories.

3. **Create migration provider/runner**:
   - Implement using Kysely's own `Migrator` class with `PostgresDialect` and `pg` driver
   - Configure PostgreSQL connection for local/test environments
   - Support reading migrations from `packages/database/migrations/`

4. **Create migration CLI commands**:
   - Script/command to apply pending migrations
   - Script/command to check migration status
   - Commands should work against empty PostgreSQL database

5. **Create minimal technical validation migration**:
   - Prefer a no-op migration that proves the framework works without creating permanent application tables
   - The migration framework's own history/lock tables are expected technical metadata
   - Only create an arbitrary application table (e.g., `migration_test`) if a genuine Kysely limitation makes that necessary
   - If a no-op migration can prove apply, migration history tracking, idempotent rerun, and rollback/down handling, use that approach
   - Must be clearly marked as technical validation only, not domain schema

6. **Create migration integration test**:
   - Test that migrations apply successfully against empty database
   - Test that rerunning with no pending migrations is safe/idempotent
   - Test that failures are surfaced and do not silently continue
   - Use Testcontainers or existing local PostgreSQL infrastructure

7. **Document migration usage**:
   - Add npm scripts for common migration operations
   - Document how to run migrations locally and in tests

## Required Tests

Migration verification must prove:

- Empty database → migration runner applies migrations successfully
- Applied migrations are tracked correctly (migration history table exists and is populated)
- Rerunning with no pending migrations is safe/idempotent from the runner perspective
- Migration failures are surfaced clearly and do not silently continue
- Integration verification uses isolated PostgreSQL (Testcontainers or local dev container)
- Production database (`finance_hub_prod`) is NEVER used in tests

Tests should cover:

- Migration apply success
- Migration status check
- Idempotent rerun (no-op when no pending migrations)
- Migration failure handling
- Rollback capability (if down migrations are implemented)
