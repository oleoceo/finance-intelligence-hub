## Implementation contract

API passes only validated generic-create command, idempotency key and request context. Core GenericCreateTransaction computes the T06 canonical fingerprint before server-controlled fields are generated. It is the sole production generic-create entry point and owns one outer `FinancialTransactionPort.runInTransaction(...)`. T02/T03/T04 type-specific executors receive that transaction context and preserve separate business policies; they never open or commit independent nested transactions.

Within the one PostgreSQL transaction: claim idempotency with the T06 conflict-safe protocol; on ownership, acquire financial locks in M03 order, re-read and validate locked state, dispatch the type-specific executor, insert Transaction, append `TRANSACTION_CREATED` Audit, complete idempotency with the Transaction resource and HTTP 201 logical status, then commit. Replay returns stored logical result without Transaction or Audit writes. Any pre-COMMIT failure rolls back all three records.

Audit new_data is the persisted Transaction snapshot, old_data=null, source=direct_api, actor_reference=null for M04's shared service credential. Correlation ID comes from request context. Never store a Bearer token, API secret or credential value in AuditEvent, logs, response, fingerprint or source_reference. A future safe principal identifier needs a later task. No Outbox emission.

## Concurrency and locking requirements

The idempotency claim serializes same-key requests through PostgreSQL `ON CONFLICT DO NOTHING RETURNING`; no ordinary unique-violation continuation on an aborted transaction. Financial locks then follow Books, Accounts, Categories, Merchants and deterministic UUID order. Lock-set-change/deadlock retries restart the entire outer transaction, including idempotency claim. A bounded exhaustion maps to 503 `DATABASE_UNAVAILABLE`; unexpected infrastructure failures map to 500 `INTERNAL_ERROR`. No independent nested financial transaction is permitted.

## Required unit tests

## Required PostgreSQL integration tests

- Successful atomic create: Transaction + Audit + Idempotency all present after commit.
- Pre-COMMIT failure rollback: none of the three rows persist.
- Same key + same fingerprint replay: same Transaction resource and 201 logical status, no duplicate Audit; request tracing metadata may differ.
- Same key + different fingerprint: 409 conflict; no new Transaction or Audit.
- Concurrent duplicate creates: exactly one succeeds; others replay or conflict deterministically.
- Audit row correctness: entity_id matches Transaction, action=TRANSACTION_CREATED, source=direct_api, new_data valid JSONB.
- Financial lock participation verified under contention.
