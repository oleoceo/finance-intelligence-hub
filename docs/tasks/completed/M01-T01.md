## 5. Stack evaluation requirements

Evaluate practical implementation options against the frozen requirements.

The recommendation must explicitly cover:

- modular-monolith suitability;
- PostgreSQL support;
- database transactions;
- row-level locking / `SELECT ... FOR UPDATE` or equivalent;
- PostgreSQL `NUMERIC(18,2)` handling without floating-point financial logic;
- migrations;
- strict request/schema validation;
- OpenAPI or executable API-contract support;
- service authentication and scopes;
- optimistic locking;
- structured logging;
- configuration validation;
- unit testing;
- real PostgreSQL integration testing;
- concurrency testing;
- Docker deployment;
- maintainability;
- dependency maturity;
- compatibility with the user's local environment.

At minimum, compare the strongest realistic candidates justified by the repository requirements. Do not create a large artificial comparison if one candidate is clearly unsuitable.

## 6. UUID validation

For the recommended stack, investigate whether a maintained and reliable UUIDv7 implementation is available.

Report:

- candidate library/runtime capability;
- maintenance maturity;
- whether application-layer UUIDv7 generation is practical;
- whether UUIDv4 fallback appears necessary.

Do not implement UUID generation yet.

## 7. No architecture invention

The stack must adapt to the frozen architecture.

Do not recommend changing financial semantics, API/domain rules, PostgreSQL as Source of Truth, or the modular-monolith baseline merely to suit a framework.
