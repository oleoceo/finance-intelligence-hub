## Implementation contract

- Transfer requires: book_id, account_id (source), destination_account_id, amount, description, transaction_date. Optional: notes, source_reference.
- Server controls: id, human_ref, status = posted, version = 1, timestamps, source, refund_of_transaction_id = null, category_id = null, merchant_id = null.
- Transfer create DTO rejects `category_id`, `merchant_id` and `refund_of_transaction_id`, including explicit null; all three persist as null.
- CreateTransfer operates within caller-provided `FinancialTransactionContext`; it does not open or commit a nested transaction. T04 tests may provide a test-owned outer context; T07 owns the production outer transaction.
- Source and destination must belong to the same Book; verified via locked Account rows.
- Source ≠ destination enforced in Core AND by DB CHECK.
- Cross-Book Transfer rejected with CROSS_BOOK_TRANSFER_NOT_SUPPORTED; never silently converted.
- Same locking protocol with BOTH Accounts locked in UUID ascending order after Book lock.

## Concurrency and locking requirements

1. Preliminary read to resolve Book, source Account, destination Account IDs.
2. Lock Book, then lock both Accounts in UUID ascending order.
3. Re-read Book and both Accounts within transaction.
4. Validate same-Book, same-currency, active, source ≠ destination.
5. Insert Transfer.
6. Return to the caller, which commits or rolls back the one outer transaction.

If preliminary read yields different Account IDs than expected, rollback and restart with corrected lock set. Never lock one Account, then discover the other requires an earlier-ranked lock.
