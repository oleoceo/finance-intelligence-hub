## Shared invariants and exclusions

Only expense/income/transfer and posted/voided. Money is exact positive decimal,
not floating point. PostgreSQL is canonical; financial date is transaction_date,
bounded by Book timezone today. Preserve Book/account/currency, Transfer shape,
immutable identity/provenance, posted-refund sum/date guards and append-only audit.
Last remains created_at DESC, id DESC among posted rows in the applicable Book.
No Refund PATCH or Refund-of-Refund. No Expense Void with posted Refunds.

Use API → Core, composition → Database, Database → Core ports, public package
exports and the existing outer transaction. Never import pg/Kysely/Fastify into Core.
Every introduced mutation must be safe immediately; P04 is not permission to ship
unsafe intermediate endpoints.

No migrations, dependency/package/lockfile changes, frozen-document edits,
unrelated refactors, new framework, M08 reporting/CSV, M09 restore, live operations,
real data or merge. No Outbox without consumer. No direct financial API under
finance:ingest. Source/actor are trusted context, not body-controlled.

## Goal and bounded implementation

Implement dedicated `POST /api/v1/transactions/{expense_id}/refunds` with
Idempotency-Key and frozen body: version, amount, account_id, transaction_date,
description, optional notes. Strictly reject client book_id/currency/type/status/
refund_of_transaction_id/provenance. Target must be a posted Expense; reject
Income, Transfer, Refund and voided targets as REFUND_INVALID_TARGET.

Lock original Expense before authoritative version/state/posted Refund aggregate
reads; enforce amount > 0 and new posted sum <= original amount. Equal boundary,
partial/full/multiple Refunds are allowed. Refund date >= original date and <=
today in Book timezone. Validate active credited Account in inherited Book/currency.
Direct API account is explicit; WhatsApp inference belongs to P05.

Insert linked Income via a dedicated repository operation, not generic create.
Reuse UUIDv7/human-ref collision handling and decimal persistence. New Refund has
version 1 and inherits Book/currency from original. Original amount/status/date are
not mutated by creation. Generic POST remains incapable of linking Refund.

Add `transactions:refund` scope and canonical fingerprint containing original
target/version and all semantic request fields. Same scoped key/request returns
the original stored result before current freshness checks; changed target or
payload conflicts. Independent keys are serialized against original aggregate.
Emit TRANSACTION_REFUND_CREATED identifying new Refund and original relation;
store trusted provenance; creation/audit/idempotency are atomic. API success 201.
Retain P01 Refund immutability and P02 Refund Void behavior.

## Acceptance criteria and required tests

- Unit: valid partial/full/multiple Refunds; exact remaining arithmetic; over-refund, zero/negative, precision/range; date lower/upper boundaries; wrong target; inherited Book/currency; account active/Book/currency; server field rejection.
- PostgreSQL: linked Income round-trip, relation/FKs, exact Money, new human_ref/version, audit relation, rollback on audit/completion failure, original unchanged.
- Independent backends: Expense 500 with concurrent Refund 300 + 300 cannot both commit; prove lock wait and final sum <= 500. Same-key duplicate produces one Refund/audit and stable replay.
- API: stale original version, missing key, changed payload/key conflict, invalid target/date/amount codes, finance:ingest denial; generic POST rejects link/type bypass.
- Regression: PATCH Refund rejected; Expense floor/date guards include newly created Refund; Refund Void releases remaining capacity.

Refund creation must already be concurrency-safe before P03 acceptance.
P04 broadens race coverage; it is not a later fix for intentionally unsafe P03.
No WhatsApp flow, summary calculation or new migration.
