## Allowed implementation surface

### packages/core

- `src/domain/finance/money.ts`: immutable Money value object with canonical two-decimal string amount and currency; validate with string/BigInt-safe logic, never Number/float.
- `src/domain/finance/transaction-types.ts`: `TransactionType = 'expense' | 'income' | 'transfer'`; `TransactionStatus = 'posted' | 'voided'`; M04 create source is `direct_api`. Do not add future-source behavior.
- `src/domain/finance/transaction-validation.ts`: pure validators for type/status/amount/currency/date invariants; validate actual YYYY-MM-DD calendar dates (including leap years), not only regex; future-date check accepts injected `now` and the locked Book IANA timezone; inactive-entity rejection helpers.
- `src/domain/finance/human-ref.ts`: application-owned injectable generator for deterministic tests; generated reference uses uppercase ASCII letters and digits (`[A-Z0-9]`), at most 16 characters. Database UNIQUE is final authority; T02 owns collision-safe persistence.
- `src/domain/finance/errors.ts`: typed financial failures mapped only to the existing public vocabulary in frozen API §10. Reuse existing master-data errors; malformed type/status/amount/date and server-controlled input map to 422 `VALIDATION_ERROR`. Do not add public `INVALID_TRANSACTION_TYPE`, `INVALID_TRANSACTION_STATUS`, `INVALID_AMOUNT` or `REFUND_BYPASS_REJECTED`.
- `src/application/ports/transaction-ports.ts`: `TransactionRepository`, `TransactionReadPort`, `TransactionRecord`, `CreateTransactionInput`, `ListTransactionsInput`, `ListTransactionsResult`, `GetLastTransactionInput`. Ports must not expose Kysely/pg types.
- `src/application/ports/idempotency-ports.ts`: `IdempotencyKeyRepository`, `IdempotencyKeyRecord`, `CreateIdempotencyKeyInput`, `CompleteIdempotencyKeyInput`, `IdempotencyFingerprint` contract.
- `src/application/ports/audit-ports.ts`: `AuditWriter`, `WriteAuditEventInput` covering `TRANSACTION_CREATED` only in M04.
- `src/application/ports/financial-transaction-port.ts`: extend or compose `TransactionPort` to support financial-write context (Transaction repository + Audit writer + Idempotency repository + Locks + Master Data readers) without breaking existing M03 configuration transactions. Prefer composition over modifying the accepted `MasterDataTransactionContextT04` shape unless necessary for atomicity.

## Implementation contract

- Money value object is immutable; equality by value; serializes to decimal string.
- Public Expense/Income/Transfer input DTOs omit `refund_of_transaction_id`; generic input is a discriminated union with only these three transaction types. Transfer input also omits category_id and merchant_id.
- M04 Money accepts only ASCII decimal strings matching `^(?:0|[1-9][0-9]{0,15})(?:\.[0-9]{1,2})?$`, with value strictly greater than zero. Leading zeroes other than `0` are rejected. No sign, whitespace, separator, exponent, NaN or Infinity is accepted. Reject more than two fractional digits, including trailing zeroes beyond two. Maximum is `9999999999999999.99` (`NUMERIC(18,2)`); reject a larger integral part or amount. Canonical internal, persistence and response form always has exactly two fractional digits (`35` → `35.00`, `35.5` → `35.50`). Compare bounds using strings/BigInt, never floating point; never rely on PostgreSQL rounding/truncation.
- Transaction validation is pure where possible; Book timezone is an explicit parameter, never imported globally.
- Financial errors carry stable machine-readable codes matching `05-API-CONTRACTS.md` §10.
- Ports are minimal and cohesive; no god-context.
- The generator's choice of format is bounded M04 implementation policy, not a frozen format. It is injected through application composition, never through production API input. T02 retries only `human_ref` collisions within one financial transaction using a PostgreSQL-safe conflict protocol, at most three generated candidates.
- All new Core exports are covered by unit tests in this task.

## Concurrency and locking requirements

T01 does not implement locking but MUST define the financial transaction context shape so that T02+ can participate in the accepted M03 lock protocol. The financial write context must include access to `ConfigurationLockPort`, `BookRepository`, `AccountRepository`, `CategoryRepository`, `MerchantRepository`, `FinancialUsageReader` and the new `TransactionRepository`/`AuditWriter`/`IdempotencyKeyRepository` within the same PostgreSQL transaction.

- Transaction types/status/source enums and guards.
- Validation: each invariant and strict calendar-date validation (`2026-02-30` invalid); future date with injected `now` and locked Book timezone.
- Human-ref: printable uppercase ASCII, length, injectable deterministic generator; collision persistence proof belongs to T02.
