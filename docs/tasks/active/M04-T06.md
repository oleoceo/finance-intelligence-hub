## Implementation contract

- Scope: `transactions:create` (or equivalent stable string) for generic create.
- Fingerprint: deterministic hash of normalized request body excluding `Idempotency-Key` header itself; stable across retries; documented algorithm.
- Same key + same fingerprint → return stored completed result without re-executing business logic.
- Same key + different fingerprint → reject with `IDEMPOTENCY_CONFLICT` (409).
- Pre-COMMIT failure rolls back idempotency record together with Transaction + Audit.
- No `failed` state in V0.1; failed attempts leave no persistent trace.
- Repository must participate in the same PostgreSQL transaction as financial writes.

## Concurrency and locking requirements

Idempotency insert uses `UNIQUE(scope, idempotency_key)` constraint as the serialization point. No additional application-level lock is required for the idempotency row itself. Financial locks follow M03 protocol independently.

On unique violation during `in_progress` insert:
- If existing row is `completed` and fingerprint matches → return stored result.
- If existing row is `completed` and fingerprint differs → `IDEMPOTENCY_CONFLICT`.
- If existing row is `in_progress` → treat as concurrent duplicate; wait/retry bounded or surface concurrency error.

## Required unit tests

- Fingerprint determinism: same input → same hash; field order independence; whitespace/normalization stability.
- Conflict detection logic: matching vs differing fingerprints.
- Scope resolution purity.

## Required PostgreSQL integration tests

- Successful `in_progress` → `completed` lifecycle within transaction.
- Same key + same fingerprint replay returns identical result.
- Same key + different fingerprint returns 409 conflict.
- Pre-COMMIT rollback removes `in_progress` record.
- Concurrent duplicate keys respect unique constraint; no orphaned `in_progress`.
- No automatic expiry column or routine exists.
