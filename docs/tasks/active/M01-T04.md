## Implementation Sequence

Execute the following steps in order:

1. **Verify Existing Docker Engine Health**
   - Confirm Docker Engine v29.8.0 is active and healthy inside Ubuntu WSL2.
   - Do not upgrade or modify the existing Docker Engine.

2. **Establish Native Node.js Toolchain**
   - Install Node.js 24 LTS natively inside Ubuntu WSL2 (via NodeSource or nvm).
   - Install pinned pnpm 12.3.4 inside Ubuntu WSL2.
   - Ensure these tools are available in the WSL2 PATH.

3. **Prevent Windows node_modules Reuse**
   - The Windows repository exists at `C:\Projetos\finance-intelligence-hub` and is visible from WSL as `/mnt/c/Projetos/finance-intelligence-hub`.
   - Do NOT run a Linux `pnpm install` in that Windows working tree if it would operate on the same Windows-side `node_modules`.
   - Preserve the Windows working tree and its dependencies; do not delete, rename, overwrite, or repurpose the Windows `node_modules`.
   - Use a clean Linux-side copy/worktree/clone or another non-destructive method when native Linux dependencies are required.
   - A symlink into `/mnt/c` does NOT count as Linux-native filesystem storage.
   - If a temporary Linux-native clone/worktree is created, it must be clearly identified as development/runtime infrastructure and must not become an independent source of truth.
   - Git history remains the synchronization mechanism between working copies.
   - Document the final chosen execution model.

4. **Empirical Execution Location Decision**
   - Evaluate performance of running `pnpm install` and `vitest` from `/mnt/c/Projetos/finance-intelligence-hub` (Windows filesystem accessed via WSL2).
   - Compare with a true Linux-native worktree (e.g., `~/src/finance-intelligence-hub`).
   - Document the decision based on actual I/O performance measurements.
   - If a native worktree is chosen, create it via Git clone or worktree.

5. **Intentional PostgreSQL Version Selection**
   - Select a PostgreSQL version based on project requirements and long-term support (do not select merely because an image exists locally).
   - Pin the selected version explicitly in the Docker Compose configuration.

6. **Create Isolated Finance Hub Configuration**
   - Create `docker-compose.dev.yml` with Finance Hub–specific naming (e.g., `finance-hub-postgres`, `finance-hub-network`, `finance-hub-data`).
   - Ensure no collision with existing Docker assets from other projects.
   - Bind PostgreSQL only to localhost or internal Docker network as needed for local development; do not expose publicly.

7. **Validate PostgreSQL Connectivity**
   - Start the Finance Hub PostgreSQL container.
   - Verify connectivity using `psql` or a simple Node.js script from within WSL2.
   - Confirm basic operations (CREATE TABLE, INSERT, SELECT).

8. **Testcontainers Smoke Test**
   - Add/use the approved Testcontainers for Node.js dependency as required by ADR-001.
   - Execute a minimal ephemeral PostgreSQL smoke test to prove Testcontainers can discover the Docker socket and manage container lifecycle.

9. **Prove Non-Interference**
   - Verify that existing Docker containers, images, volumes, and networks belonging to other projects were not modified or deleted.

## Local PostgreSQL Credentials & Security

- **No Real Secrets:** No real secret or credential may be committed to the repository.
- **Local Configuration:** Local PostgreSQL credentials must use ignored local environment/configuration (e.g., `.env.local`, `.env`) where appropriate.
- **Placeholders Only:** `.env.example` may contain placeholders only (e.g., `POSTGRES_PASSWORD=changeme`).
- **No Public Exposure:** PostgreSQL must not be exposed publicly. If a host port is required for local debugging, bind explicitly to loopback (`127.0.0.1:5432`) rather than all interfaces (`0.0.0.0`).
- **Production Isolation:** Never use production credentials or the `finance_hub_prod` database for local development or testing.
