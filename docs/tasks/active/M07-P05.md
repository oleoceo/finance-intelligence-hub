## Goal and bounded implementation

Extend existing deterministic Interpretation/ResolutionResult, process-message and
reply presentation to correction/void/refund intents. Reuse M06 normalized ingestion
and reply delivery unchanged. Frozen examples: "corrige último para 38,90",
"cancela último", "estorna 200 da compra A83K2P".

Resolve explicit human_ref or contextual candidates within the applicable Book;
capture Last target ID/version immediately using created_at DESC, id DESC.
Never resolve "último" again on confirmation. Refund fallback candidates follow
human_ref → merchant/amount/date/context → recent candidates → choice. No arbitrary
winner on ambiguity. Credit original account only when valid and unambiguous;
otherwise request a choice.

A clear ordinary Correction may execute directly only with unambiguous target,
fields/change and valid captured version. Choice-driven Correction can use
ConfirmationSession. Every WhatsApp Void and Refund, including Refund Void and
fully clear requests, requires explicit confirmation; no response means zero effect.

Persist target_entity_type=transaction, target_entity_id, target_version on any
Transaction-targeting session. Extend advanceChoice narrowly if target becomes known
after a choice, atomically binding ID/version to the displayed proposal. A target
selection is not implicit consent to Void/Refund: present destructive proposal and
require explicit yes afterward. Preserve sender ownership, TTL, expiry, cancel,
supersession and original/resolver Inbox fencing.

Under the shared lock protocol execute P01–P03 caller-owned use cases in the same
transaction as confirmation resolution and Inbox finalization. Revalidate version,
target state, current posted Refund aggregate and reference validity at execution.
A changed version performs zero mutation and returns a bounded stale/revalidate
reply; never silently update captured version and execute. Freshness errors must
not leave a falsely confirmed session. Failed/cancelled/expired paths retain a
coherent lifecycle and no financial effect.

Extend finalization proof for mutation actions: require target/result and matching
audit/effect evidence in the current operation, not merely any historic audit for
that target. No confirmed terminal state without successful effect. Correction/Void
must not overwrite the target's original inbox_message_id; audit/idempotency links
track the command. Refund links new row to original command Inbox. Durable keys for
Void/Refund derive from original Inbox/action; direct Correction duplicate protection
uses existing atomic Inbox claim/finalization. Repeat replies never duplicate audit,
version increments or linked Income. Preserve trusted source/actor and reply bounds.
