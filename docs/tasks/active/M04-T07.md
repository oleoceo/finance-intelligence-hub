## Goal

Compose Transaction creation, Idempotency and Audit into a single atomic PostgreSQL operation for generic create. This task wires the three write paths (Expense/Income/Transfer) through idempotency orchestration and emits `TRANSACTION_CREATED` audit events in the same transaction. No query behavior or API routes are introduced here.

## Implementation contract

- Generic create flow:
  1. Compute fingerprint from normalized request body (T06 contract).
  2. Within financial transaction context:
     a. Attempt `in_progress` idempotency insert.
     b. On unique violation: check completed row → replay or conflict.
     c. Acquire financial locks per M03 protocol (Book → Account(s) → Category → Merchant).
     d. Re-read authoritative state; validate invariants via T02/T03/T04 use cases.
     e. Insert Transaction.
     f. Write `TRANSACTION_CREATED` audit event.
     g. Complete idempotency key with response metadata.
     h. Commit. Rollback on any failure removes all three writes.
- Audit `new_data` contains the full persisted Transaction record as JSONB; `old_data` is null for create.
- Correlation ID flows from API request context through to audit; T07 accepts it as explicit parameter.
- Source is `direct_api` for M04 generic create.
- No Outbox emission in M04.

## Concurrency and locking requirements

Financial locks follow M03 protocol exactly. Idempotency unique constraint provides serialization for duplicate keys. The total order within the financial transaction is:

1. Idempotency `in_progress` insert (unique constraint as lock).
2. Book lock → Account lock(s) → Category lock → Merchant lock (per M03 ordering).
3. Re-read + validate + insert Transaction + write Audit + complete Idempotency.
4. Commit.

On deadlock or `ConfigurationLockSetChangedError`, retry per accepted bounded protocol. Surface `ConcurrencyError` after exhaustion.

## Required unit tests

- Orchestrator routing: expense/income/transfer dispatch to correct use case.
- Fingerprint integration: same input produces same key lifecycle.
- Audit payload construction: correct entity_type, action, source, new_data shape.
- Replay path: completed idempotency returns stored result without re-executing business logic.
- Conflict path: different fingerprint triggers IDEMPOTENCY_CONFLICT.
- Error propagation: business validation failure prevents audit and idempotency completion.

## Required PostgreSQL integration tests

- Successful atomic create: Transaction + Audit + Idempotency all present after commit.
- Pre-COMMIT failure rollback: none of the three rows persist.
- Same key + same fingerprint replay: identical Transaction returned; no duplicate Audit.
- Same key + different fingerprint: 409 conflict; no new Transaction or Audit.
- Concurrent duplicate creates: exactly one succeeds; others replay or conflict deterministically.
- Audit row correctness: entity_id matches Transaction, action=TRANSACTION_CREATED, source=direct_api, new_data valid JSONB.
- Financial lock participation verified under contention.
