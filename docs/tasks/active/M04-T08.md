## Implementation contract

- POST `/api/v1/transactions`:
  - Requires `Authorization: Bearer <admin-token>` and `Idempotency-Key`.
  - Accepts only `expense | income | transfer` type.
  - Rejects `refund_of_transaction_id` in generic create.
  - Returns created Transaction with `status = posted` or replayed result.
  - Maps financial errors to exact codes/statuses.
- GET `/api/v1/transactions`:
  - Supports filters: `book_id`, `type`, `status`, `account_id`, `category_id`, `merchant_id`, `date_from`, `date_to`, `search`.
  - Pagination: `page` default 1, `page_size` default 50, max 100.
  - Deterministic ordering: `created_at DESC, id DESC`.
- GET `/api/v1/transactions/last?book_id=<uuid>`:
  - `book_id` required; returns most recently created posted Transaction or null.
  - Uses `ORDER BY created_at DESC, id DESC` via partial index.
- GET `/api/v1/transactions/:id`:
  - Returns Transaction or 404 `TRANSACTION_NOT_FOUND`.
- All routes require `finance:admin`; `finance:ingest` receives 403.
- Error envelope matches `05-API-CONTRACTS.md` §9; success envelope matches §8.

## Required unit tests

- Schema validation: unknown fields rejected; missing required fields; invalid type/status/date/amount.
- Idempotency-Key enforcement: missing key → 422; present key → forwarded.
- Error mapping: each M04 financial code maps to correct HTTP status.
- Auth: admin token accepted; ingest token rejected; no token → 401.

## Required API/PostgreSQL integration tests

- Create Expense via API: 200 + correct response shape + DB row + audit event.
- Create Income via API: ordinary income only; refund bypass rejected.
- Create Transfer via API: same-account/cross-book/currency-mismatch rejections.
- Replay: same Idempotency-Key + same body → identical response; no duplicate DB rows.
- Conflict: same key + different body → 409 IDEMPOTENCY_CONFLICT.
- Get/List/Last: correct filtering, pagination, ordering, empty results.
- Last semantics: posted-only, created_at ordering, book isolation.
- Auth boundary: ingest token cannot access any transaction route.
- Unknown field rejection on POST.
- Future transaction_date rejection via API.
- Inactive master data rejection via API.
- Prove M04 works without Evolution/n8n/AI/Firefly/Metabase (no imports, no runtime dependencies).
