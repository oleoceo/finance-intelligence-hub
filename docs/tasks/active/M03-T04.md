## Classification Rule configuration

- CreateClassificationRule validates priority (integer), match_type exact/contains, raw pattern plus normalized_pattern, and at least one target. Server sets source=manual, ID/timestamps and initial active=true.
- UpdateClassificationRule merges PATCH with locked current state and validates the entire resulting target configuration. source is server-controlled and never client-writable. No new source/system internal flow.
- Database §34 explicitly assigns target compatibility and active state to Core. Each non-null Book/Account/Category/Merchant target must exist and be active for create/update, including unchanged targets and active=false configurations. Resolve Account/Category owning Books and check active context too.
- All supplied/derived Book contexts must agree. Do not require an explicit target_book_id when Account or Category alone supplies context: database §§33–34 permits independent nullable targets, and its CHECK requires only one. Account-only, Category-only and Merchant-only rules remain valid. Merchants are global.
- If a target is archived later, retain the Rule and its references. A later PATCH must replace/remove inactive targets, retaining at least one valid target. No cascading deactivation/rewrite or runtime matching is implemented.
- Rule active=false is deactivation, not four-entity archive. Get/list may include inactive rules. Stable configuration order is priority ASC, created_at ASC, id ASC (bounded list tie-breaker, not new M05 precedence behavior).

Ledger §97/domain §63 runtime inactive-target avoidance, explicit instruction precedence, message matching and alias application remain M05. T04 tests normalization/configuration round trips only, not an Inbox matching engine.

## Authorized Sender configuration

- CreateAuthorizedSender accepts channel, sender_reference, optional name/defaults and optional active (default true). API §27 explicitly includes active in the create request, so it is not an unknown/server-controlled field here.
- channel is a nonempty string up to VARCHAR(32); no exhaustive frozen enum exists (database §36; API §27 is an example). sender_reference is a nonempty string up to VARCHAR(255), stored unchanged. Identity uniqueness is (channel, sender_reference), enforced by M02.
- UpdateAuthorizedSender allows name, defaults and active. Identity fields are excluded from PATCH as a bounded configuration API choice; do not claim frozen universal identity immutability.
- default_account_id requires default_book_id; Account must belong to that Book; every non-null default must be active, including when the Sender is inactive. Validate merged PATCH state so clearing only Book while Account remains is rejected. Explicit null clears defaults.
- Deactivation changes active only. It does not remove defaults and therefore does not lift T02 archive protection. No Inbox authorization, raw persistence or WhatsApp transport.

## Concurrency and reader ownership

Follow the overview's explicit FOR UPDATE protocol, held to commit, total entity/UUID ordering, re-read after locking and full retry if the discovered lock set changed.

Rule writes lock explicit/derived Books, Accounts, Categories and Merchants before the Rule row and before target checks. Archive operations lock the same referenced rows. If configuration commits first, later target archive remains permitted; if archive commits first, new/updated configuration fails with the target's *_INACTIVE code.

Sender writes/removal lock old/new Books then Accounts, followed by the Sender row on update. Book/Account archive uses those same referenced locks before default queries. Assignment-first blocks archive; archive-first rejects assignment; removal-first permits archive. Never claim that transaction wrapping alone solves the race.

T02 already supplies SenderDefaultReferenceReader and its working Database adapter. T04 reuses/composes that single capability, rather than duplicating reference queries inside the full AuthorizedSenderRepository or retroactively making T02 depend on T04.
