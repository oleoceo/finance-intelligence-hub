## Cycle prevention and concurrency

Use the overview lock protocol. Every Category write first locks its Book FOR UPDATE as a per-Book hierarchy mutex, then any affected Category rows in UUID order. Read the proposed parent's ancestor chain after acquiring the Book lock. Core rejects self-parent and any ancestor path reaching the moving category; a visited set terminates traversal safely if corrupt/preexisting cyclic data is observed. Missing/cross-Book parents fail validation before mutation.

The lock serializes hierarchy changes even when their directly updated categories differ. Test simultaneous A-under-B and B-under-A: after the first commit, the second sees the new ancestry and fails CATEGORY_CYCLE. Include longer, disjoint-row moves that together would close a cycle. Release on rollback; do not rely on administrator frequency, sequential usage or ordinary READ COMMITTED checks without locks.

A single new server-ID category referencing an existing acyclic parent cannot by itself create a longer cycle under the existing FK model. Longer-cycle tests therefore exercise UpdateCategory/reparenting, not a fictitious create-only cycle. The Core algorithm consumes parent links from a repository port; SQL traversal/data retrieval is an adapter detail, not the owner of domain policy.

## Merchant uniqueness and archive decision

Domain §§48–54 defines global Merchants and historical retention. Database §§28–29 defines INDEX(normalized_name), not UNIQUE; M02 intentionally accepts duplicate normalized names. Create/update must accept them, including concurrent inserts. Normalization is for lookup/matching; any name lookup returns multiple candidates and is never a uniqueness gate.

CreateMerchant/UpdateMerchant support name, nullable type and nullable tax_identifier within physical lengths; no invented tax format or tax uniqueness. No Book association or alias table/CRUD. ArchiveCategory/ArchiveMerchant remains permitted with historical financial references, per ledger §§82–83 and domain §§46/54. Preserve all references and historical reads. No financial-reference archive guard, dormant scaffold or later M04 activation. Future financial creation and M05 application must reject inappropriate inactive use in their own milestones.

Category/Merchant archive locks the same target rows used by T04 Rule configuration. Rule-first may retain a subsequently archived target; archive-first prevents new configuration using it. Do not block archive merely because a Rule references it.
