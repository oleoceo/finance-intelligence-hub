## Implementation contract

- Scope exactly `transactions:create`; Idempotency-Key is a nonblank UTF-8 string of at most 255 characters.
- Core computes SHA-256 lowercase hexadecimal (exactly 64 characters) over deterministic canonical JSON of the validated generic-create command before server-controlled generation. JSON object keys are sorted deterministically; array order, if any, is preserved. The command contains type, book_id, account_id, transfer destination_account_id when applicable, T01 canonical two-decimal amount, description, transaction_date, and applicable optional category_id, merchant_id, notes and source_reference.
- Preserve semantic string content exactly, including internal whitespace in description/notes/source_reference. Do not trim arbitrary user text. For applicable optional category_id, merchant_id, notes and source_reference, omitted and explicit null mean the same value and serialize as null. Transfer has no category/merchant DTO fields and they are absent from its canonical shape.
- Exclude Idempotency-Key, Authorization, request_id, correlation_id, and server id/human_ref/status/source/version/timestamps/currency derived from Book.
- Same key/hash plus completed record replays the same Transaction resource and 201 success status without executing writes. HTTP request_id and correlation_id are fresh for each request. Different hash gives 409 `IDEMPOTENCY_CONFLICT`.
- Store enough canonical result in the existing `response_status` and `response_body` columns to reproduce the logical `data` and status, without reusing an old HTTP tracing envelope.
- The idempotency claim, Transaction, Audit and completion share one PostgreSQL transaction. Pre-COMMIT failure rolls all back; no failed state or expiry is introduced.

## Concurrency and locking requirements

Use `INSERT ... ON CONFLICT (scope, idempotency_key) DO NOTHING RETURNING ...`. Inserted row owns execution. No row means read the existing key after PostgreSQL conflict serialization: different hash conflicts; same hash + completed replays. For same hash + in_progress, use a finite PostgreSQL lock wait and re-read under row lock; if still in_progress, roll back and retry the entire outer transaction, at most three attempts. A finite database lock timeout also causes a fresh outer-transaction attempt. No busy-loop. Winner rollback allows a retry to become owner. Never catch a plain unique violation and continue on the aborted transaction.

Whole financial-transaction retry restarts the idempotency claim and financial locks together. Bounded wait/lock retry exhaustion maps through existing 503 `DATABASE_UNAVAILABLE`. PostgreSQL remains sole authority; no Redis.

## Required PostgreSQL integration tests

- Successful `in_progress` → `completed` lifecycle within transaction.
- Same key + same fingerprint replays the same resource and 201 status; HTTP tracing metadata may differ.
- Same key + different fingerprint returns 409 conflict.
- Pre-COMMIT rollback removes `in_progress` record.
- Concurrent duplicate keys respect unique constraint; no orphaned `in_progress`.
- No automatic expiry column or routine exists.
