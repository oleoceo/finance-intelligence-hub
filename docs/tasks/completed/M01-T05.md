## Logging and Security Requirements

- All application logs must be structured JSON suitable for machine parsing.
- Every log entry associated with an HTTP request must include `request_id`.
- When a `correlation_id` is present (from validated header or fallback), it must also appear in relevant request-associated log entries to enable cross-request correlation.
- `request_id` and `correlation_id` are required on request-associated application log entries, not unrelated startup/process logs.
- Fields only meaningful at request lifecycle/completion stages (route, method, status, duration) do not have to be artificially populated on every child log entry.
- `error_code` is present only when applicable.
- Sensitive values must never appear in plaintext in logs:
  - Authorization headers
  - Cookies
  - Passwords
  - API/service credentials
  - Database credentials
  - Raw secrets
- Additionally:
  - Do not log `process.env`;
  - Do not log raw request bodies wholesale;
  - Do not log complete raw header objects unless the configured serializer/redaction makes the relevant sensitive fields safe;
  - Tests must assert against actual emitted structured log output so secret values are proven absent/redacted.
- Raw WhatsApp message text should be minimized in operational logs; its controlled location is the authorized InboxMessage record.

## Request/Correlation Identifier Behavior

- **`request_id`**: Always a newly generated server-side UUIDv7 for each HTTP request, produced through Fastify's request-ID mechanism as the single authoritative source. Never uses an externally supplied value. Used to correlate all log entries within a single request lifecycle. Available from the Fastify request context and emitted in request-associated logs under the canonical field `request_id`.

- **`correlation_id`**: Extracted from the canonical incoming header `X-Correlation-ID` (case-insensitive lookup). If a valid value exists (exactly one string, trimmed length 1–128 characters, allowed characters `[A-Za-z0-9._:-]`), it is preserved as `correlation_id`. If absent or invalid (empty, multiple, oversized, malformed, control-character-containing), `correlation_id` is set equal to `request_id`. Invalid values must not cause request failure solely because of correlation metadata and must not be echoed into logs. No persistence is performed; no distributed tracing semantics are introduced.

- Identifiers must be deterministic and testable.
- Malformed or untrusted externally supplied identifier values must not break logging or create unsafe behavior.
- Do not persist these identifiers in Redis, PostgreSQL, or any external store during M01-T05. They exist only in request context and logs.
