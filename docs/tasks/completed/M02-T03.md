## Exact scope and schema objects owned

Own only transactions and its PK/FKs/unique constraints/CHECKs/indexes. Implement exact types, lengths, nullability and defaults in database §55:

- Required UUID id; human_ref VARCHAR(16); book_id UUID.
- type/status VARCHAR(16); amount NUMERIC(18,2); currency VARCHAR(3).
- Required account_id; nullable destination_account_id/category_id/merchant_id.
- Required description VARCHAR(500); nullable notes TEXT.
- Required transaction_date DATE; required source VARCHAR(32); nullable source_reference VARCHAR(255) and inbox_message_id UUID.
- Nullable refund_of_transaction_id UUID self-reference.
- version INTEGER NOT NULL DEFAULT 1.
- Nullable voided_at TIMESTAMPTZ and void_reason TEXT; required created_at/updated_at TIMESTAMPTZ.

UUIDv7 remains application-generated. human_ref is separate and unique; generation behavior belongs to M04. Do not add occurred_at, balance, is_refund storage, financial time-of-day, FX columns or separate Refund/Correction/Void tables.

## PK/FK/UNIQUE/CHECK responsibilities

- UUID PK; UNIQUE human_ref; UNIQUE (id, book_id, currency) to support same-context refund linkage.
- book_id→books.id and (book_id, currency)→books(id, currency).
- Source (account_id, book_id, currency) and nullable destination (destination_account_id, book_id, currency) reference accounts(id, book_id, currency).
- Nullable (category_id, book_id)→categories(id, book_id); merchant_id→merchants.id; inbox_message_id→inbox_messages.id.
- refund_of_transaction_id→transactions.id plus documented composite (refund_of_transaction_id, book_id, currency)→transactions(id, book_id, currency).
- Partial UNIQUE inbox_message_id WHERE NOT NULL: at most one financial Transaction per originating Inbox. Multiple direct-API rows with NULL Inbox are valid.
- Types exactly expense|income|transfer; statuses exactly posted|voided; amount > 0; version >= 1; uppercase three-letter currency.
- Expense/Income have no destination; Transfer requires a different destination Account and no refund reference. Any non-null refund reference requires type income.
- Posted requires both voided_at and void_reason null; voided requires both non-null.
- Restrictive deletion preserves history. No active-state FK, clock-based date CHECK, business trigger or cross-row refund CHECK.
