## Acceptance

- Resolve Book in frozen order: explicit instruction → applicable safe ClassificationRule → valid active AuthorizedSender default → single eligible active Book → clarification/confirmation. Resolve Account within that Book in frozen order: explicit instruction → applicable rule/deterministic alias → valid active AuthorizedSender default → single eligible active Account → clarification/confirmation. M05 acceptance uses no AI; optional AI cannot override explicit values or bypass safety checks. A missing or multiple eligible candidate never selects arbitrarily. Stable rule priority/tie handling cannot silently pick an ambiguous target. Supplied references are not overridden.
- Resolve Book, Account, Category and Merchant against active records and compatible Book/currency/type. Never apply inactive rule or inactive target. Merchant remains global but active. Ambiguous names/aliases yield confirmation rather than arbitrary selection. Resolved command must satisfy M04 input and guards again at write time.
- For create, use the resolved Book timezone to turn an omitted date into the received local date, evaluate `hoje`/`ontem`/`anteontem` and pt-BR dates, then reject a date later than the current Book-local date. Preserve explicit date provenance. For `query_last`, resolve an explicit Book such as `empresa`, otherwise a valid sender default or the single eligible active Book; ambiguous/missing context requires clarification. Do not resolve an Account or create input for this read.
- Concurrent configuration changes must not authorize stale/inactive references. Follow M03 lock rank and whole-transaction retry if discovered references change after ordered locking. No late lower-rank lock acquisition.
