## Routes and success contract

For each base below expose POST base (Create), GET base (List), GET base/{id} (Get) and PATCH base/{id} (Update including lifecycle), totaling exactly 24 routes:

| Base | Core entity/use cases |
| --- | --- |
| /api/v1/books | Book |
| /api/v1/accounts | Account |
| /api/v1/categories | Category including reparenting |
| /api/v1/merchants | Merchant |
| /api/v1/admin/classification-rules | ClassificationRule |
| /api/v1/admin/authorized-senders | AuthorizedSender |

All routes, including reads and the four bases without /admin, require valid Bearer credentials with finance:admin. Authenticate and check scope before schema/domain work: missing/invalid credentials -> 401 UNAUTHORIZED; valid ingest-only/no-admin credential -> 403 INSUFFICIENT_SCOPE, even with an invalid body. Reject before any use-case invocation or mutation. No new authentication platform or sender-ingestion authorization.

Bounded success choice where frozen is not explicit: POST -> 201; GET/PATCH -> 200. API §8 success envelope is {data, meta:{request_id,correlation_id}}; a resource operation returns one persisted configuration resource, List returns an array. Use explicit response schemas from the corresponding database §§14/17/23/28/30/36 resource columns: UUID IDs, strings/enums, boolean active, nullable reference/text fields, server timestamps serialized as RFC3339 strings. The first four have nullable archived_at; Rule/Sender do not. Rule response may expose server source and normalized_pattern; derived normalized_name may be returned for the four name-bearing entities. Never expose credentials, SQL or connection details. Preserve existing request/correlation-ID behavior.

## Deterministic write schemas

Use strict TypeBox object schemas with additionalProperties=false and validation that rejects extra fields rather than silently stripping them. No mass assignment; explicitly build DTOs from declared fields. Unknown fields, including client server-field values equal to the server's value, are rejected.

The frozen documents provide create examples but not exhaustive PATCH schemas; this table is the bounded M03 request contract for human review. Required create fields are marked with an asterisk; all PATCH fields are optional, with at least one supplied field required. Omitted PATCH means unchanged; null is allowed only where stated.

| Entity | POST fields | PATCH fields |
| --- | --- | --- |
| Book | name*, currency*, timezone (default America/Sao_Paulo) | name, currency (Core usage guard), timezone, active |
| Account | book_id*, name*, type*, institution_name nullable, notes nullable | name, type (Core usage guard), currency (Core usage/equality guard), institution_name nullable, notes nullable, active |
| Category | book_id*, name*, parent_category_id nullable, type (default both) | name, parent_category_id nullable, type, active |
| Merchant | name*, type nullable, tax_identifier nullable | name, type nullable, tax_identifier nullable, active |
| Classification Rule | priority (default 100), match_type*, pattern*, target_book_id/target_account_id/target_category_id/target_merchant_id nullable | priority, match_type, pattern, same four nullable targets, active |
| Authorized Sender | channel*, sender_reference*, name nullable, default_book_id/default_account_id nullable, active (default true) | name nullable, same nullable defaults, active |

At least one Rule target must survive after create/merged PATCH. For Sender, Account default requires Book default. Account POST currency is derived from Book (API §17); clients cannot override it in this selected schema. Book/Account/Category/Merchant/Rule create active is server-set true and rejected if submitted. Sender create active is explicitly allowed by API §27, including false, but does not bypass default validation. PATCH active=false archives the first four entities and only deactivates Rule/Sender; active=true restores the first four by clearing server archived_at. Rule PATCH always validates its complete effective targets as specified in T04, even for deactivation.

Always reject id, normalized_name, normalized_pattern, archived_at, created_at, updated_at and ClassificationRule.source on writes. Also reject undeclared human_ref, status, version, voided_at, refund_of_transaction_id or any other extra field. Server IDs/timestamps/normalized values/source are never accepted or silently ignored. Account/Category book_id and Sender channel/sender_reference are undeclared on PATCH and therefore rejected. API §§5–6 and §§23–24 govern strict fields/source; security §63's softer wording does not override API §5.

Validate UUID syntax, booleans without coercion, integer priority within PostgreSQL INTEGER range, uppercase three-letter currency, IANA timezone <=64, Account type checking/savings/cash/credit_card/other, Category type expense/income/both, Rule match_type exact/contains. Names/patterns must be nonblank and raw/normalized values fit storage limits: Book name 120; Account/Category name 160; Merchant name 200; Rule pattern 500. Other physical limits: institution_name 160; Merchant type 50/tax_identifier 32; Sender name 160/channel 32/sender_reference 255. Nullable free-text notes has no invented business format. No Merchant tax uniqueness or format rule.

AuthorizedSender.channel is a nonempty bounded string, not an enum: database §36 is VARCHAR(32), API §27 gives an example rather than an exhaustive vocabulary. Do not reject an otherwise valid channel just because it differs from that example. Store sender identity unchanged.

## Read filters and order

Path IDs use UUID validation. Bounded list filters: all entities accept active; Accounts accept book_id; Categories accept book_id, parent_category_id (UUID), type; Rules accept match_type and target_book_id; Senders accept channel. Unknown/malformed query fields are rejected. Omitted filters include archived/inactive configuration; no financial Last semantics.

Stable selected ordering: Books/Accounts/Senders created_at DESC, id DESC; Categories/Merchants normalized_name ASC, id ASC; Rules priority ASC, created_at ASC, id ASC. Tie-breakers are configuration-list choices, not new matching precedence. No extra endpoint or speculative pagination subsystem.

## Deterministic errors

API §§9–10 provides the envelope/code vocabulary but does not prescribe a complete entity/status matrix. The following single mapping is a bounded interpretation for this milestone. Never expose raw database errors or choose a status according to whether a precheck or constraint detected the problem.

Error envelope: {error:{code,message,details},meta:{request_id,correlation_id}}. Details contains only safe field/reason identifiers. Generic mappings below use the documented VALIDATION_ERROR code rather than inventing entity-specific public codes.

| Condition | HTTP | Code / safe details reason |
| --- | --- | --- |
| Missing/invalid credential | 401 | UNAUTHORIZED |
| Valid credential without finance:admin | 403 | INSUFFICIENT_SCOPE |
| Malformed JSON | 400 | VALIDATION_ERROR / malformed_json |
| Well-formed request failing body/path/query schema; extra/server fields; empty PATCH | 422 | VALIDATION_ERROR / invalid_request |
| Missing Book/Account/Category/Merchant, requested or referenced | 404 | corresponding BOOK_NOT_FOUND / ACCOUNT_NOT_FOUND / CATEGORY_NOT_FOUND / MERCHANT_NOT_FOUND |
| Missing Rule/Sender resource | 404 | VALIDATION_ERROR / resource_not_found |
| Inactive target/default/context | 422 | corresponding BOOK_INACTIVE / ACCOUNT_INACTIVE / CATEGORY_INACTIVE / MERCHANT_INACTIVE |
| Direct self-parent or longer category cycle | 422 | CATEGORY_CYCLE |
| Category parent from another Book | 422 | VALIDATION_ERROR / category_parent_book_mismatch |
| Account currency differs from Book | 422 | CURRENCY_MISMATCH |
| Changed Book currency after dependencies; changed Account type/currency after use | 422 | VALIDATION_ERROR / immutable_field |
| Incompatible Rule contexts or zero targets | 422 | VALIDATION_ERROR / incompatible_targets or missing_target, respectively |
| Sender Account default without Book | 422 | DEFAULT_ACCOUNT_REQUIRED_BOOK |
| Sender Account default in different Book | 422 | DEFAULT_ACCOUNT_BOOK_MISMATCH |
| Book/Account archive still referenced by any sender default | 409 | DEFAULT_BOOK_IN_USE / DEFAULT_ACCOUNT_IN_USE, respectively |
| Duplicate Book/Account/Category normalized name in its actual unique scope, or duplicate sender identity | 409 | VALIDATION_ERROR / duplicate_configuration |
| Repeated discovered-reference change/deadlock after three full transaction attempts | 409 | VALIDATION_ERROR / configuration_changed |
| Database unavailable | 503 | DATABASE_UNAVAILABLE |
| Unexpected internal failure | 500 | INTERNAL_ERROR |

Duplicate Merchant normalized names are successful, not errors. Known M02 UNIQUE violations use the same 409 mapping as any optional precheck; Category self-parent CHECK maps to CATEGORY_CYCLE. Map recognized FK/CHECK violations to the corresponding safe validation reason above; an unrecognized database failure is INTERNAL_ERROR, not leaked SQL. Core controls deterministic validation order: request shape, resource existence, lifecycle immutability/default dependency, relationship compatibility/cycle, active state, persistence uniqueness. For multiple missing/inactive targets use Book, Account, Category, Merchant order; check all relevant existence before relationship validation. Validate Sender missing-Book dependency before attempting a missing Book lookup. Retries roll back the whole transaction; they never retry a partially committed mutation.
