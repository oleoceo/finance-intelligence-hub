## Acceptance

- Filter group and `from_me` before Inbox/financial persistence. Normalize sender deterministically and reject invalid references. An active sender must be checked and locked/re-read before raw text insert; unauthorized/inactive sender returns the frozen 403 `SENDER_NOT_AUTHORIZED` at the eventual route and leaves zero raw Inbox records.
- Use unique `(source, source_instance, source_message_id)` as identity. Concurrent duplicates return one row. Processed and ignored rows are terminal; duplicate processed does not reexecute. Failed retry reclaims the same row and increments `attempt_count`. Stale `processing` recovery uses a bounded operational timeout, same row and a fenced claim; old claimant cannot finalize after replacement.
- Preserve `received → processing → needs_confirmation → processed | failed | ignored` and valid direct terminal transitions. Set `processing_started_at`, `last_attempt_at`, `processed_at`, `failure_code/message` consistently; never store sensitive raw text in failure/log fields. Do not invent a new database status.
- P01 may leave an authorized claimed row for P05 to process, but P05 owns atomic terminal Inbox plus financial effect. Expose transaction-scoped repository capability for that composition. The pre-persistence sender lock/re-read and raw Inbox insert occur in their own committed authorization/claim transaction; do not carry that Sender lock into P05's later financial transaction. P05 must lock all required configuration references in M03 rank before its authoritative Sender revalidation and financial effect. A revoke between initial ingest and effect must prevent execution.
