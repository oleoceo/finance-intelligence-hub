## Implementation contract

- Expense requires: book_id, account_id, amount (decimal string), description, transaction_date (YYYY-MM-DD). Optional: category_id, merchant_id, notes, source_reference.
- Server controls: id (UUIDv7), human_ref, status = posted, version = 1, created_at, updated_at, source = direct_api (or T01-defined default). Client never supplies these.
- Generic create input never exposes `refund_of_transaction_id`, including explicit null; T08 strict schema rejects it. Persist `refund_of_transaction_id = null` for Expense.
- Future transaction_date uses Book.timezone resolved from locked Book row inside the same transaction.
- Inactive Book/Account/Category/Merchant rejected BEFORE insert with specific error codes.
- Financial lock: acquire Book lock, then Account lock (and Category/Merchant locks if referenced), re-read active state, validate, insert. Follow M03 lock ordering exactly.
- On lock-set-changed or deadlock, the outer financial transaction retries the whole operation under the accepted bounded protocol; T08 maps exhaustion to 503 `DATABASE_UNAVAILABLE`.
- The application-owned injectable human_ref generator emits `[A-Z0-9]` up to 16 characters. Insert with `ON CONFLICT (human_ref) DO NOTHING RETURNING ...`; regenerate and retry only that conflict, at most three generated candidates inside the same PostgreSQL financial transaction. Do not catch an ordinary unique violation and continue on an aborted transaction. Exhaustion is an internal/infrastructure failure mapped to 500 `INTERNAL_ERROR`; no new public financial code or API test-mode input.
- CreateExpense neither opens nor commits a transaction. T02 tests may call it inside an explicit test-owned financial context; T07 owns the production outer transaction.

## Concurrency and locking requirements

Mandatory participation in M03 lock protocol:

1. Preliminary read to resolve Book/Account/Category/Merchant IDs from input.
2. Acquire locks in order: Books → Accounts → Categories → Merchants. UUID ascending within each kind.
3. Re-read authoritative state within the same transaction.
4. Validate all invariants against locked state.
5. Insert Transaction.
6. Return to the caller, which commits or rolls back the one outer transaction.

Never acquire Book lock after Account lock. Never skip re-read after locking.
